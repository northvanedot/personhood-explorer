What the tier does and does not establish

Read from the pallet source. The tier is not read off registration. The precompile calls personhood_info(account, context), which returns nothing unless the account holds an alias in that context. The tier then comes from which ring collection that alias belongs to — PEOPLE_LITE_IDENTIFIER → Lite, PEOPLE_IDENTIFIER → Full.

Binding an alias costs a fee, AliasFee, and while it is None every set_alias_account fails with AliasFeeUnset. Since runtime v2.5 the fee is a root-only runtime parameter rather than pallet storage, and it defaults to None — the Asset Hub runtime's own comment notes it has never been set on Paseo. It is unset on this devnet.

So no alias can be bound, and every account reads None — Lite and Full are both unreachable here, not just Full. A None on this devnet says nothing about the account at all.

What registration does and does not establish

Read from the pallet source. PeopleLite.LitePeople has two entry paths, and they are not equivalent.

UniqueDevice An attester holding an allowance granted by AttestationAllowanceManager submits attest. The chain verifies the candidate's signature, a ring-VRF proof of key ownership, and that the key is not already in the collection.
Fee register_with_fee: the candidate pays and proves key ownership. No attester and no uniqueness check of any kind.

In neither case does the chain establish a human. Under UniqueDevice, one person per record is the attester's claim — the chain checked signatures, not people. Under Fee nobody claims it: nothing stops one person registering repeatedly with fresh accounts and fresh keys, paying each time.

What an alias would establish

Per the pallet docs, an alias is the same person across sessions within one context, and a different context yields a different alias that cannot be linked to it. That is the privacy property the design rests on — and all of it is read from the pallet source.

This app has never observed one, because none can exist here. Nothing below has been seen working on this devnet.

One limit is structural rather than cryptographic: AccountToAlias is a public map holding one alias per account. The unlinkability is between aliases in different contexts, not between an account and its alias — so using one account across two contexts defeats the property the alias exists to provide.

A separate registry from usernames — owning northvane.02 gives no claim on northvane.dot. Short names need personhood as well as the price.
